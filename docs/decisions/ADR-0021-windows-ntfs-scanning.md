# ADR-0021 — Windows local NTFS read-only scanning

Date: 2026-10-30. Status: accepted for the owner's explicit Windows-backend continuation; distribution and untested filesystem gates remain open.

The owner requested working Save & Start scanning on Windows, a prominent alert for unsupported selections, then a commit and PR. Folder selection alone previously failed to open directories; after that fix, native identity/volume/traversal were still Unsupported. Implement the actual read adapter rather than fabricate identity or bypass the action's guard.

Keep Windows API calls in `crates/core/src/filesystem/windows.rs`, with the scanner adapter in `library/scan_windows.rs`. Reuse catalog actors, filters, root IDs, resource admission, revision checks, jobs and the supervised media worker. Pin the already-resolved `windows-sys` 0.61.2 directly for Foundation/FileSystem/Security bindings; no new runtime binary, application identifier, schema migration or existing identity rewrite.

Limit this slice to local NTFS with a native volume GUID. Retain the complete GUID token separately from the filesystem serial and 64-bit NTFS file index. Refuse other filesystems and network volumes; do not compress ReFS's wider identity into the old catalog fields. Capture file and volume identity in the native picker session, bind both to registration/relink, and revalidate saved roots before/after scans and original reads. File IDs are observations, not permanent content identity or independent-device protection.

Enumerate through held directory handles using `GetFileInformationByHandleEx`, a fixed 64 KiB aligned buffer, checked record/name bounds and exact UTF-16 names. Open observed child IDs through `OpenFileById`, with no-recall/no-reparse flags, exact native-name/ID membership checks before/after opening, and no write/delete sharing. Each enumeration gets an independent handle/cursor. This avoids depending on undocumented RootDirectory/OBJ_DONT_REPARSE combinations. Final metadata checks reject every reparse/offline/recall entry before reading bytes. Sharing restrictions reject ordinary data writers/renames but are not a universal snapshot or a guarantee against all attribute changes, privileged writers or filesystem defects.

Membership checks intentionally scan directory entries again. Memory stays bounded, but a very large flat directory can incur quadratic lookup work. No Windows large-library throughput, P4 performance, network-event completeness or physical-I/O guarantee is established here. Preserve failures/incomplete scopes; missing/offline/replaced roots must never become empty successful inventories. Keep the existing depth/cancellation limits and exclude the app-owned data directory by identity as well as location.

Use the existing supervised baseline decoder for Windows dimensions, orientation and content digest. Keep filesystem date provenance when capture metadata is unavailable; record the `windows-basic-v1` limitation explicitly. JPEG/PNG/WebP can render through the existing worker/cache. Windows ExifTool packaging, capture/camera/GPS extraction, RAW/HEIC/ICC expansion and larger format envelopes are separate gates. Unsupported files remain indexed with explicit errors.

The Windows cache adapter alone publishes an app-generated, flushed and closed stage via a no-replace hard link. Its stage and destination are private cache paths; conflicting bytes are retained/rejected. The generic original-file publication primitive, directory durability and original mutation guard remain unavailable on Windows. This cache exception must not be reused as an operation executor.

Validate native IDs, exact names, multi-batch enumeration, junction escape, root/volume replacement, filters, source-read cancellation, cache conflicts, real generated-library IPC/previews and source manifests. Keep macOS, signed packaging, clean machines, other filesystems and every original-mutation/recovery gate explicit. Actual outcomes belong in [the implementation log](../IMPLEMENTATION_LOG.md).

Primary contracts: [directory handles](https://learn.microsoft.com/en-us/windows/win32/fileio/obtaining-a-handle-to-a-directory), [file-ID opens and their flags](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-openfilebyid), [directory record layout/alignment](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_both_dir_info), [volume information](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationbyhandlew), [volume GUID paths](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew).
