# ADR-0016 — Prepare previews before first collection reveal

Date: 2026-10-30. Status: accepted for the owner's initial-scan request within M1.

Keep discovery and thumbnail decoding as separate bounded read-only jobs. Persist one initial thumbnail job in the existing scans table when a folder is scanned for the first time: `thumbnail:initial:<root UUID>`. Its queued state covers discovery; the normal executor resumes the same job after discovery finishes. This gives cancellation, restart and progress a durable identity without changing schema 2, root/catalog UUIDs or existing library state. Legacy completed libraries receive no marker or migration.

Photos/Tags collection queries carry the optional typed deferPendingPreviews flag. Pending/placeholder entries are omitted only for roots whose initial preparation has not resolved. Apply the same predicate to count, pages, dates, seeks, neighbors and frozen selection; preserve all other filters and metadata. Raw catalog and folder inspection remain available. Keep existing inventory/index fast paths when no matching initial preparation is active. A ready publication advances the library revision so a bounded feed refresh can introduce the photo. Per-tier failures remain explicit unavailable states rather than silently dropping files.

The first thumbnail job is reserved before discovery starts, then admitted to the existing runtime queue after discovery; it does not read originals while waiting. Queued cancellation shares the thumbnail admission mutex with the handoff. Cancellation/failure/interruption retains the initial gate and a Resume previews action; reconciliation never undoes the pause. Only an explicit resume resets the job. Successful/partial completion must atomically confirm no eligible current revision is still pending/placeholder; otherwise retain a failed resumable preparation. This guards source/catalog changes after a job's inventory snapshot.

Use a compact temporary banner above the collection, retaining header Jobs and the current canvas. Discovery is indeterminate because the final file count is unknown. A counted thumbnail inventory supplies processed/remaining figures, counting generated, cached and unavailable outcomes distinctly. Queued/running-before-inventory states must not claim zero remaining. Paused/failed work remains visible with the actual reason and ID-only resume. Text list remains image-free and shares this initial collection scope so view changes preserve selection/anchors.

Rejected alternatives: doing image decoding in the scan loop would block discovery and bypass the established scheduler; filtering only the loaded renderer page would strand pagination and totals; hiding pending previews for every existing library would disturb cache clearing/offline browsing. No original operation, new dependency, native helper or permission is introduced. A bounded 45-second initial-job hold exists only under fixture-probes, invoked through the existing desktop-test diagnostic permission with an owned fixture, to inspect real native progress before source admission. Production excludes it; it is not latency evidence.
