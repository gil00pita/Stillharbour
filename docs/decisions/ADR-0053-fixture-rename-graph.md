# ADR-0053: Bounded rename ordering and a closed native fixture

Date: 2026-11-01
Status: experimental fixture work; M2 gate remains open

## Decision

Keep same-root rename ordering in `operations/rename_graph.rs`, separate from filesystem adapters. A plan binds stable member IDs, exact leaf names, source/root revisions and adapter-observed native name equivalence. All changed sources move to distinct private stages before any final publication, permitting case-only changes and cycles without replacement. Unknown/offline name evidence, conflicting target classes, occupied stages and unrelated target occupants produce no executable steps. Reverse planning reconstructs the exact canonical forward record, uses fresh revisions/name facts and reports new occupants of old names. Its serialized `execution_available` always remains false.

`executor/rename_fixture.rs` is compiled only for tests or `fixture-probes`. It accepts no caller paths, plans or file contents. Its constructor creates five distinct generated byte streams, including a companion, a case-only change, a cycle and an ordinary rename. These are filesystem test payloads, not decoder-support fixtures. Exclusive empty probes observe equivalence on the exact generated parent; probes are retained under private names before originals are created. No lowercase/Unicode guessing supplies native facts.

The closed fixture uses the existing no-replace native publication primitive, atomic root leases, shared paced I/O, complete byte comparisons against retained local versions, original object IDs and modification-time/readonly/available-creation-time checks. A separate FULL-synchronous SQLite journal records ordered intent/completion facts and per-phase native revisions. An interrupted publication is reconciled by exact original object identity and fresh complete-byte inspection, with a new one-use fixture action approval. Completion facts are not blind replay authority. Reverse execution gets a new graph, fresh native name observations and separate approval; a new occupant of an old path blocks before moves. The fixture approval is synthesized by the test harness; it is not a user approval flow.

## Limits and next gate

Local retained versions are on the same development storage. They do not establish independent recovery, native ACL/xattr/resource-fork fidelity, physical disconnection, power-loss durability or production authorization. Current interruptions are in-process; after an unrecorded native move, complete bytes/essential metadata and exact original identity must be revalidated, while the pre-move change timestamp cannot prove what occurred during that gap. Recovery under process termination, journal failure/source races and catalog/UI integration still require implementation and evidence. Default real-library mutations remain disabled. M3 cannot begin until the actual M2 gate passes.

## Validation

Run the focused `rename_graph` and `native_rename_fixture` Rust cases with `fixture-probes,copy-workflow`, followed by the documented full, separate-feature-graph, desktop and release checks. Record actual results in `IMPLEMENTATION_LOG.md`; a proposed probe or passing pure test is not native acceptance.
