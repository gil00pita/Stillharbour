# Stillharbour - Preservation and Backup & Sync acceptance scenarios

Version 1.1 supplement | 2026-10-23

**These are 40 required test specifications, not tests that have run or passed.** They supplement the 85 original AC scenarios. Use only generated/disposable fixtures. Record native Windows/macOS and actual transport evidence for the behavior being advertised.

| ID | Area | Scenario | Required result |
| --- | --- | --- | --- |
| PS-001 | Read-only audit | Scan, hash, compare, thumbnail and integrity-check generated roots containing sidecars and unusual names. | No source byte, path or descriptive-metadata changes. Account separately for OS access-time updates. Compare creates no target-tree files. |
| PS-002 | Damaged/unknown input | Include truncated images, unknown extensions and undecodable RAW files. | Preserve all inputs. No automatic repair, rewrite, rename or deletion. Diagnosis distinguishes unsupported, inaccessible and corrupt. |
| PS-003 | Scope versus visibility | Hide a file in the gallery and add hidden sidecars and non-photo regular files. | Full-library protection still inventories them. Explicit omissions and unsupported objects prevent a false whole-folder protection claim. |
| PS-004 | Default-root binding | Change the default library after saving a profile. | Profile remains bound to its original root UUID until explicit rebinding and fresh review; no destination removals are inferred. |
| PS-005 | Destination containment | Select source itself, descendants, ancestors, symlink aliases, junctions and multiple paths to the same tree. | Unsafe overlap/escape is rejected in backend planning and execution. No recursive backup or alias-based write-through. |
| PS-006 | Source availability | Deny a directory listing or disconnect the source halfway through compare. | Do not reinterpret failure as absence or empty scope. Keep destination-only files and previous inventory; report incomplete comparison. |
| PS-007 | Destination-only protection | Place unique files and manually edited photos only at the destination. | Safe sync retains them. Existing destination ownership is not assumed merely because its parent was selected. |
| PS-008 | False quick equality | Use different files with the same path, length and timestamp; restore old timestamps after an edit. | Quick compare is unverified. Full content comparison detects the difference. Cached time/size evidence never authorizes cleanup. |
| PS-009 | Retained replacement | Approve replacement of one differing destination file with two earlier retained revisions. | All three previous revisions remain uniquely recoverable. Source is unchanged; new content passes verification before commit. |
| PS-010 | History creation failure | Deny history writes, exhaust history quota, or cause retained-copy verification to fail. | Replacement stays blocked. Old destination and source remain intact; no Force action bypasses the gate. |
| PS-011 | Late destination arrival | Create or replace the target after preview or immediately before publish. | No-replace/conditional publication prevents overwriting the unexpected object; re-review is required. |
| PS-012 | Concurrent source edit | Modify source during transfer, including a same-length rewrite and timestamp restoration where detectable. | Evidence is invalidated on detected changes; no source cleanup. Document limitations of undetectable external writes; do not claim universal race immunity. |
| PS-013 | Crash at every stage | Terminate after intent, during staging, after flush, during verification, during history preservation, after publish and before catalog commit. | Reconcile on restart. Every previous source/destination version is intact or recoverable. No blind destructive replay or false completion. |
| PS-014 | Full disk | Exhaust space during staging, history save, final flush and catalog journaling. | Pause or fail safely. No automatic deletion of history/originals. Published partial files never masquerade as complete copies. |
| PS-015 | Network interruption | Drop SMB/SFTP connectivity in each transfer/commit phase and restore it. | Preserve source; identify partial and uncertain commits; revalidate endpoint identity and resume only from proven state. |
| PS-016 | Reused storage identity | Replace a removable disk at the same drive letter or map a different share at the same mount path. | Stop before writes. A matching path string is insufficient. Explicit relink and new review are required. |
| PS-017 | Ambiguous remote result | Server commits publication but the acknowledgement is lost. | Inspect actual objects/versions and journal before retry. Never duplicate a destructive replacement or erase a version by replay. |
| PS-018 | Skip and keep-destination status | Skip one failure and keep destination for a differing source revision. | Job reports the uncopied revisions explicitly and remains partial/scoped; no full protection badge or mutation-gate evidence for those items. |
| PS-019 | Verification mismatch | Inject one-bit destination corruption and wrong remote checksums. | Read-back comparison rejects the item. Existing source/history survive. No Accept anyway or source quarantine becomes available. |
| PS-020 | Safe restore | Restore to a target containing different files, then interrupt. | Default restore uses a separate staged/new directory. Existing content is not truncated or overwritten; an in-place action requires its own protected plan. |
| PS-021 | Rollback conflict | Occupy an original path with new content before undo. | Undo becomes a conflict-safe reverse plan. Both versions survive; rollback is not unconditional overwrite. |
| PS-022 | Bundle uniqueness | Two identical JPEGs have different or unique RAW, motion, XMP or ACR companions. | JPEG equality does not authorize dropping unique companions. Incomplete copied bundles cannot unlock source cleanup. |
| PS-023 | Metadata fidelity | Use xattrs, permissions, resource-fork/ADS fixtures and unsupported destination metadata. | Report exact fidelity limitations; do not destructively relocate essential unsupported data. Byte equality alone is not full-fidelity evidence. |
| PS-024 | False independent copy | Use another hard link, same-volume clone, second partition or unknown NAS backing store as recovery evidence. | No automatically verified independent-device claim. Require appropriate separate failure-domain evidence/explicitly labelled owner declaration; protect against aliasing. |
| PS-025 | Strict mutation gate | Attempt real-library rename/quarantine before recovery evidence exists, then after the protected source revision changes. | Backend blocks both cases. Read-only/verified-copy work remains available. M2/M3 fixture tests do not unlock production mutations. |
| PS-026 | Recovery retention | Request pruning/expiry of a version referenced by an unfinished operation or recovery record. | No automatic prune. Explain the dependency; refuse removal while it would undermine an active recovery guarantee. |
| PS-027 | Partial cleanup ownership | Mix application staging objects with unknown temporary files and user-created names. | Cleanup touches only positively identified owned objects under a journaled plan, never guesses based on suffix alone. |
| PS-028 | Hostile paths and manifests | Supply traversal paths, separators, reserved Windows names, Unicode collisions and reparse changes during execution. | Containment and native collision rules hold; no escape, silent path collapse, lossy execution-path conversion or overwrite. |
| PS-029 | Transport trust | Present unknown/changed SSH host identities or invalid TLS certificates; inspect logs for secrets. | Fail closed with explicit trust resolution. No generic ignore. No credentials or private path/GPS leakage in exported diagnostics. |
| PS-030 | Unsupported publish capability | Use a remote lacking reliable no-replace/conditional publication or essential fidelity support. | Offer tested append-only version output or block replacement. Do not emulate safe overwrite with a race-prone existence check. |
| PS-031 | Shared-device resource accounting | Run comparison, transfer and thumbnail jobs against two paths on the same physical device. | One effective device budget applies where identity is known; concurrency and read/write budgets are not multiplied by job or path. |
| PS-032 | Paced transfer envelope | Use a fake clock/instrumented I/O with small and large files across concurrent workers. | At each measured interval, application-issued bytes respect configured rate plus stated burst allowance. No full-file burst before sleeping. |
| PS-033 | Verification load | Enable full read-back and byte comparison over a slow network destination. | Verification and history reads consume the appropriate read/download budget. Display their extra I/O; do not cap upload only and claim all activity capped. |
| PS-034 | Live throttling and pause | Change caps repeatedly; pause during copy, verification and commit boundaries. | Apply limits at safe boundaries without corrupting state or silently skipping verification. Resume revalidates source/destination evidence. |
| PS-035 | Helper limitations | Choose a backup helper without enforceable source-disk pacing. | Unsupported control is visibly unavailable or labelled limited. Tests do not assert physical-disk guarantees from an upload cap or process priority. |
| PS-036 | Protocol round trip | For each advertised readable-sync and snapshot target, copy/backup fixtures, remove only disposable source, restore, then compare bytes/metadata. | Record native OS, filesystem/server, version and actual evidence. Snapshot tests do not substitute for ordinary-file replacement tests. |
| PS-037 | Safety action scoping | Try to reuse an approval after changing target, policy, selected rows, file revisions or companion scope. | Approval digest becomes invalid. Resolve actions cannot bypass protected roots, content checks, source identity or backup evidence. |
| PS-038 | Retained-version collision | Create many replacements with identical timestamps and colliding filenames; exhaust space during the next one. | History uses unique immutable identities. Older versions survive; lack of room pauses, not rotates away history. |
| PS-039 | Catalog and key recovery | Interrupt catalog snapshot/migration; restore with missing root mappings or wrong/lost secret. | Retain a consistent pre-operation catalog; explain relinking and key dependency. Never fake successful restore or store recovery secrets in plaintext exports. |
| PS-040 | Corrupt source propagation | Source becomes suspicious/damaged after a good backup; destination retains the earlier good version. | No automatic repair/overwrite of the only known-good version. Preserve both, expose evidence and require a distinct reviewed recovery decision. |

## Release evidence

Map every scenario to automated/native/manual tests, fixture generation, exact stages injected, commands, outcomes and untested limitations. For each mutation stage, compare source, destination, retained versions, companions, metadata, catalog and journal against preconditions. Retain a manifest proving where each original version survived.

Any unexplained loss, truncation, unreported exclusion, overwrite of an unapproved revision, missing recoverability, unsafe path traversal, or false verification claim blocks release. Passing Linux-only tests does not establish Windows/macOS behavior. Do not test destructive paths on a personal photo collection.
