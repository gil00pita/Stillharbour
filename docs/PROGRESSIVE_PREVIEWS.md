# Progressive previews and background thumbnail jobs

Owner-approved scope, 2026-10-28: a bounded P2 rendition slice for large JPEG, PNG and TIFF previews, separate background thumbnail generation and a tiny-to-clear gallery transition. This does not complete P2 or authorise P3/P4, a new decoder dependency, catalog migration or original-file changes.

After a completed/partial scan publishes its inventory, a separate **Thumbnails** job prepares 32-pixel placeholders. Scanning does not decode these renditions. Jobs in the header shows queued/running work, actual generated/cached/unavailable counts, cancellation and retained history. **Generate thumbnails** selects a saved library and backfills existing catalogs without a rescan. Restart marks interrupted jobs honestly; an explicit generation pass resumes by reusing indexed positives. Cancel retains completed previews. Unavailable items remain explicit.

Clear 256/512-pixel previews are requested for visible photos and viewer navigation. The gallery and folder icons request both tiers, with at most 240 visible assets / 480 tier keys; each backend batch remains capped at 64. A tiny cached image stays visible until the clear image's load event, then a 400 ms opacity/2 px cross-blur reveals it without layout movement. Reduced-motion preferences disable the transition. A failed clear preview retains its usable tiny image; errors are scoped separately to each of the three tiers. Text-only browsing still requests no images.

## Safety and resource boundaries

- The backend reopens a catalog-authorised original through native root/volume/identity containment. The macOS decoder child receives an inherited **read-only regular-file descriptor**, never a renderer path or executable. The provider uses bounded `pread` callbacks; it never writes an original or maps the entire input.
- ImageIO downsamples JPEG/PNG/TIFF directly to the requested edge. This replaces their obsolete full-source RGBA _estimate_ rejection with a bounded rendition path. Other native types retain their previous full-source estimate and 32 MiB encoded-input limit. The portable byte decoder retains its 128 MiB allocation cap. No Windows large-file downsampling claim is made.
- File-backed inputs are capped at 512 MiB, native callback reads at 480 MiB plus at most 32 MiB header/ICC reads. Each dimension remains capped at 12,000 px. Returned PNGs remain at most 512 px / 2 MiB with bounded JSON output. Extreme/unsupported files can still fail explicitly.
- Preserve strict JPEG/PNG ICC validation, ColorSync sRGB RGBA8 rendering, alpha, one orientation transform, primary/first-frame policy and no upscaling. Preview success is not full-media validation or archival color-fidelity evidence.
- Retain two shared media permits, the foreground queue of 64, cancellation, 12-second deadline and the macOS direct-child RSS watchdog (512 MiB sampled every 25 ms). This is not an instantaneous allocator or helper/XPC process-tree quota. One background job runs at a time; at most eight jobs are admitted, coalesced per root, with catalog pages of 64 and a row high-water mark. Clear previews remain demand-driven.
- Retain the indexed 256 MiB cache bound, protected publication/readback and revision checks; positive M5-v2/M1 cache entries remain readable offline. No blanket cache purge occurs. Large libraries can exceed the cache capacity and need regeneration of evicted entries. The new policy retries obsolete negative results without rewriting schema 2 on open.
- Maintenance rejects queued/running thumbnail jobs until they finish or are canceled; the user must review the action again. It cannot delete a library while a job republishes its previews. Missing/excluded assets are omitted from background inventory; native placeholder checks prevent implicit cloud downloads.
- Durable thumbnail jobs reuse the existing job/issue tables with backend-generated `thumbnail:<UUID>` IDs and a typed `thumbnails` kind. Their completion/recovery never marks assets missing, changes `last_scan`, starts automatic rescans or grants mutation authority. See [ADR-0011](decisions/ADR-0011-progressive-renditions.md).

## Reproduction and evidence

From the repository root, with the pinned Node/Rust toolchains:

```sh
node scripts/cargo.mjs build --locked -p stillharbour-core --bin stillharbour-media-worker
python3 scripts/renditions/run.py
npm run check
npm run desktop:test:build
npm run desktop:test:formats
```

The [large-image runner](../scripts/renditions/run.py) creates only a fresh `.context/renditions/<UUID>` fixture, ownership marker and generated 8000×6000 JPEG/PNG/TIFF files. It exercises 32/512-pixel worker output, malformed/over-dimension inputs and refusal of a writable descriptor. Independent SHA256/size/mtime/device/inode manifests are captured before/after; sources and evidence are retained. It cannot accept a user library path. It is a single-run correctness diagnostic, not a percentile, cold-cache or complete-media benchmark.

The current local file-backed worker probe produced 32×24 and 512×384 renditions for all three generated 48 MP types, including a 144,013,004-byte TIFF. The final release diagnostic also includes Display-P3 JPEG/PNG: the legacy byte path reproduces the exact dimension/memory-budget error, while file-backed 32/512 px outputs succeed. Untagged 48 MP JPEG/PNG can already succeed on the old Rust path; they are not presented as reproductions of that failure. The initial standalone ImageIO prototype remains exploratory evidence only. Native Windows, clean-machine/minimum-OS, broader camera variants and full P2 acceptance remain unverified.

A diagnostic invocation initially passed the standalone-only `--media-worker` flag to the app executable; the app entered normal startup and was stopped on timeout. That run is excluded from fixture evidence and does not establish untouched personal catalog/cache state. No personal-data cleanup or rollback was attempted. App startup now rejects unrecognised `--media-worker*` modes before GUI/catalog initialization.

The file-backed bridge regression includes invalid ICC, alpha/channel order, read-only handle enforcement and unchanged bytes.
- Native macOS WKWebView605.1.15 debug: all13 desktop regressions pass on an isolated copy of the test binary, including the deterministic completed-scan schedule. Separate native gallery/viewer test passes tiny/clear image dimensions and loaded-state reveal, manual thumbnail backfill, original mutation exclusion and independent36-file manifests. The desktop fixture retains its32-file manifest and reports the two deliberately malformed images as unavailable thumbnail items while its scan completes without errors. Native selectors identify scan versus thumbnail jobs explicitly.
- Unsigned macOS application builds34.13MiB. Production capability/dependency/test-route exclusions and the pinned ExifTool manifest pass. Release run `7f7502b5-ba04-475b-aa0a-9e83d72c6182` passes14 image cases, a writable-descriptor negative and three legacy byte-budget negatives; its seven source files match independent before/after manifests. Packaged format regression run `45d3ec0b-3636-4012-846b-1d74f3482a17` passes18 declared generated/camera cases with matching source manifests. These are local arm64 results, not signed/clean-machine/Windows certification.
- React Doctor remains73/100 with the same10 incumbent warnings after simplifying the changed image/job renderers. The design detector reports three pre-existing palette literals; no new design finding is introduced.

Retained diagnostic failures include a misplaced copied native binary failing Tauri resource-path resolution, a temporary config discovering zero specs (not a pass), a native wait returning a DOM element instead of a serialized boolean, and old scan-only test selectors/count assertions encountering the new thumbnail job. Correct the harness/resource location and scope scan assertions while independently requiring the thumbnail job's truthful partial counts; no decoder limits, original manifests or safety assertions were relaxed. The first sRGB fixture did not force explicit ICC on the old path; Display P3 provides the actual red/green budget reproduction. Failed/canceled attempts remain under `.context/renditions` rather than being reported as passes.

No p50/p95/p99, cold-cache, process-tree memory or new throughput claim is made. Trace storage can drop bounded samples; sampled child RSS is incomplete by design and is not an instantaneous quota. Broad P2, Windows, minimum-OS, OS reduced-motion manual review and remaining preservation/platform gates remain open. The current native driver binary preserves the tested behavior; the final renderer extraction is separately covered by the passing component checks.

## Tall JPEG budget correction — 2026-10-29

[ADR-0015](decisions/ADR-0015-tall-jpeg-previews.md) supersedes the 12000-side limit only for macOS file-backed JPEG downsampling: at most 16384 per side and 144000000 total pixels, preserving the previous maximum source-pixel envelope. PNG/TIFF/other adapters and byte/full-raster paths retain their prior side limits; memory, timeout, read, output and source safety checks remain. True image-library limit failures now report the explicit preview-budget message rather than implying a decode failure. The supplied 8192×12288 JPEG produces 32/256/512/1024/2048px previews with unchanged source identity/hash in the local worker probe.

Policy p2-v3-tall-jpeg-srgb8-preview retries obsolete negative results when visible items request previews. Retain compatible positive p2-v2/p2-v1/M5/M1 cached renditions, original catalog identities and historical failed job records. No rescan, blanket cache clearing or original conversion is necessary. User-provided media and its previews/evidence remain ignored under .context/jpeg-decode/; committed regressions use generated media only. Full repository/native results and limitations are in the implementation log; this is a bounded bug fix, not later-phase completion or Windows codec evidence.

Run `node scripts/cargo.mjs test --locked -p stillharbour-core file_backed_tall_jpeg` and `node scripts/cargo.mjs test --locked -p stillharbour-core file_jpeg_still_rejects`, then the standard repository/native checks. Build `stillharbour-media-worker` before rerunning the existing generated rendition diagnostics; their PNG over-dimension negative remains valid. Only test the reported attachment through an explicitly authorized owned copy, never a real library as a fixture.
