# M4 application acceptance audit

Audit date: 2026-11-02. Scope: the current M4 application integration, the 40 scenarios in [PRESERVATION_TESTS.md](PRESERVATION_TESTS.md), and AC-066–073/081/084 in [ACCEPTANCE_TESTS.md](ACCEPTANCE_TESTS.md). This is an evidence map, not an all-M4 acceptance certificate. Stop before M5 remains applicable.

The owner authorized all M4 stages and generated local disposable servers. That authorization does not satisfy an untested preservation gate. Default production backup execution remains gated. Windows native tests now cover private old-destination snapshot admission/restore and a bounded native metadata policy. A generated C:/E: round trip also proves that the actual independent-device classifier can admit those distinct devices. These results do **not** constitute a strict old-destination replacement certificate: the tested `RecoveryFile` objects deliberately have `essential_metadata_digest: None`, and the provider still rejects them. Synthetic replacement proofs do not supply that missing authority. The generated local Windows desktop lifecycle passes; the full preservation matrix and macOS application acceptance remain open.

## Evidence boundaries and checks actually observed

- `npm run build`: passed strict TypeScript and Vite production compilation with the final generated `SnapshotRequest::Reconcile` contract and interrupted-snapshot inspection UI. Vite reports its existing large-chunk advisory.
- `npm test`: passed 64 files / 398 tests at this checkpoint, including the final profile-refresh/private-OLD-restore regressions. Coverage includes stable inspected rows during transfers, interrupted-snapshot inspection/fresh restores, independent policy disablement with bounded scheduled-job discovery, immediate/polled canonical repository-state refresh, and recorded-root validation for private OLD restores. These are frontend/component tests, not native filesystem or protocol acceptance.
- Interrupted backup inspection now has an explicit profile/job/concrete-snapshot request, returning a separate `reconcile` job. The UI offers it only for interrupted backup jobs, validates the new job identity and never retries backup, removes locks or deletes history. Failed/ambiguous inspection remains unresolved. Interrupted restores require a fresh new-output restore review. Native cold-recovery acceptance remains separate from these component states.
- Scoped ESLint, Prettier and `git diff --check` passed for the changed backup frontend and new native lifecycle specification.
- [m4-application.e2e.mjs](../tests/desktop/m4-application.e2e.mjs) first passed its Windows desktop/real-IPC lifecycle in 92.1 seconds; screenshot review then found stale top-level repository metadata. After that fix, the updated native spec **passed in 26.1 seconds**, driving actual UI review/acknowledgment/approval/start, requiring a concrete initialized repository identity after completion, and checking the qualified “last observed” source-access label. `.context/m4-application/native-8OdpGY/snapshot-lifecycle.json` and screenshot record backup, full checks, browsing, exact recurring consent/disablement, generated source removal, earlier-snapshot restore and byte/catalog/neighbor audit. The full Windows desktop command subsequently passed three spec files in 2m40s: ten tests passed and seventeen platform/opt-in tests skipped. The M4 lifecycle passed again in 28.5 seconds, with artifacts under `.context/m4-application/native-NIlSQg/`. The private-OLD recorded-root restore guard is separately component-tested.
