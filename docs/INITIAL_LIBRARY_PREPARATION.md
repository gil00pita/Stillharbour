# Initial library preparation

Owner request: 2026-10-30. New photos should enter the collection after a thumbnail has been generated, with a top progress banner and a remaining count when known. This is a bounded M1 refinement; all original-file, platform and recovery gates remain unchanged. [ADR-0016](decisions/ADR-0016-initial-preview-preparation.md) records the durable job and visibility decision.

## Behavior

On the first scan of a saved photo folder, the scanner records metadata without rewriting originals. Photos/Tags withhold pending/placeholder image entries during initial preparation; they appear progressively when their tiny previews are published. Unsupported/failed previews remain explicit outcomes with an unavailable reason. Collection counts, timeline buckets, paging, viewer seeks and frozen selection use the same initial-ready scope. Ordinary catalog queries and Folders metadata remain available, and the Text list still requests no images. Existing completed libraries, positive caches, cache clearing and root identities keep their previous behavior.

The compact banner sits above the canvas without replacing navigation or header Jobs. Following the owner's condensed-banner request (2026-10-30), its normal state is a single row: remaining count, inline 6px progress bar and Stop scan / Pause previews. With 8px vertical padding and a 36px action, it occupies 53px including the bottom border. Discovery shows “Remaining unknown” with an indeterminate bar; it never invents an undiscovered remaining count. After discovery, the existing separate thumbnail job has a fixed eligible-media inventory and the banner shows the actual remaining count. Queued and zero-inventory running states stay indeterminate, following [ARIA progressbar guidance](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/progressbar_role). The progress description remains available to assistive technology; repeated headings, folder names and processed/total copy do not occupy extra rows. The folder label is retained in progress accessibility text and the banner tooltip; detailed counts/history remain in Jobs. Unavailable outcomes, paused-job messages and action errors remain visible when present. Completion removes the temporary banner. Changing folders discards old action feedback.

Stop scan and Pause previews use only native job IDs. A queued initial job can be canceled before source admission, and the automatic handoff cannot undo that cancellation. Cancellation/failure/interruption preserves indexed observations and the visibility gate across restart. Resume previews explicitly reuses the initial job and already-owned cache; ordinary reconciliation cannot silently resume a pause. Read-only retry may still fail with an explicit root, cache, source-change or worker error. If the request was accepted but status refresh fails, report that separately rather than repeat the action as if nothing started.

At initial-job completion, check current eligible rows atomically with the terminal state. Pending revisions or newly discovered rows keep preparation resumable instead of revealing an unfinished collection. Generated previews do not prove integrity or backup protection. Cache eviction, disconnection and actual browser image loading retain their ordinary explicit loading/failure behavior; this change removes the long initial generation-placeholder phase, not every possible rendering delay or unsupported-media state. No dependency/schema/index migration or original-file operation is included.
